# Shipping fulfillment, labels, and tracking

Read when enabling ecommerce shipping. Market/provider defaults are in [Shipping service selection](#shipping-service-selection); explicit user choices take precedence. These are workflows to implement, not capabilities already provided by the generator.

## Shipping service selection

When delivery, tracking or fulfillment is selected, read the target market from initial requirements plus any known warehouse origins, destinations, carrier contracts and provider choices first. By default, shipping destinations/coverage are the target market already provided; do not ask the user to repeat the market or pricing currency. Ask about additional destination markets only if broader or cross-border delivery is indicated. Ask for a missing warehouse origin when it affects provider eligibility. Follow [Country-and-route shipping SDK/API recommendations](../shipping-providers.md) and present two or three qualified candidates for each actual route. Country starts the shortlist; origin -> destination and required capabilities determine whether it can be used. Conversation/site language, timezone and IP do not establish a route or user country. Ask only for meaningful missing country/route facts and reuse known answers.

For domestic mainland-China routes start with Kuaidi100/Kdniao; for China-origin cross-border evaluate Easyship, Shippo or the AfterShip Shipping product. US/Canada, UK/Europe, Australia/New Zealand, India and other international origins have their own shortlists in the guide. These are candidate preferences, not account/coverage guarantees. Explicit provider choices and valid existing integrations take precedence; updated guidance does not authorize migrating historical shipments or providers.

Record whether the selection came from the user or a default and its actual route coverage. Do not describe an inferred default as an explicit user confirmation. Skip this module when unnecessary; a default does not establish an account or API access.

Implement [Shipping fulfillment, labels, and tracking](#aggregator-integration-by-route): domestic China aggregators require electronic label requests, tracking numbers, print data, and printing. China cross-border and markets outside China require order submission and tracking-number return. All routes retain manual entry/editing and tracking. A tracking number or printed label is not proof of dispatch; confirm actual shipping separately.

Record routes, providers, product capabilities, and implementation status. Tracking-only or number-entry support is not full fulfillment. Use current official SDK/API documentation for fields, carriers, fees, account permissions, and callback verification. Without credentials, show the unconfigured state and allow manual recording without invented numbers, labels, or tracking events. Buying real labels or services is outside default local verification.

## Customer delivery methods and fees

For shipped-goods checkout, provide customer-selectable delivery methods such as Standard, Express, and Overnight/Next-day when applicable. This is a store delivery option and is separate from the carrier/provider used by staff to fulfill the order. Do not require a shipping-provider integration just to offer manually fulfilled delivery methods.

Provide an admin-managed list of delivery methods with at least name, customer-facing description, estimated delivery time/window, enabled/disabled status, fee, and display order. Allow admins to create, edit, enable, and disable methods. Delivery estimates should be configurable per method and shown at checkout; do not invent guaranteed delivery dates. Fee rules may be flat by default; add weight, order-total, zone, or free-shipping rules only when the brief requires them. Scope options to the configured destination market/zone when applicable. Disabled methods are hidden from checkout and cannot be submitted by tampering with the client request.

At checkout, list all enabled methods applicable to the shipping address with their description, estimated delivery time, and fee, and require the customer to select one before placing the order. Revalidate the selected method and calculate its fee on the server using current admin configuration; never trust a browser-submitted fee. Include the selected delivery fee in the authoritative order total and payment amount. Persist the selected method and a snapshot of its name, description, estimate, and fee on the order so later admin edits do not rewrite existing orders. If no eligible method is available, explain that delivery is unavailable for the address and block checkout until the address or configuration changes.

Admin delivery-method configuration and customer carrier tracking have distinct purposes: the customer's choice expresses the requested service level, while fulfillment records the actual carrier, tracking number, and dispatch state. If a selected service level cannot be fulfilled, expose an explicit admin correction workflow and preserve the original order choice/audit history; do not silently substitute it.

## Country-aware address library

For shipped-goods checkout, provide a country/region address library so customers select structured address components instead of typing every administrative area. Choose the hierarchy per country (for example, China: province -> city -> county/district; United States: state -> county/city as appropriate; other countries may use state/province -> district/municipality or a different number of levels). Do not force one global fixed hierarchy on every country. Default the country to the configured shipping market; expose a country selector only when multiple destination countries are enabled.

Prefer complete, maintained address datasets for each enabled destination country. When a reliable dataset is available and its license permits bundling, import it into the project's database rather than fetching a large static dataset on every checkout. Record dataset source, version/update date, country coverage, hierarchy depth and known gaps; normalize country/region codes and parent-child relationships, and provide a repeatable seed/import/update path. Do not label partial or stale data as complete. Keep address lookup usable from local persisted data and avoid depending on an external geocoding API for ordinary checkout.

Use cascading selectors that load only valid children of the selected parent and prevent mismatched province/city/county combinations. Populate postal codes from the chosen locality/address records where the country's postal system supports reliable mapping, and let the customer select an available code. Postal codes are not universal: where a country has no postal codes or the dataset cannot map them reliably, make the field optional or a clearly validated manual field instead of showing a misleading dropdown. Allow a street/building/unit detail field for the part that administrative datasets cannot represent. Validate submitted region IDs/codes and their parent chain on the server, and persist both structured IDs/codes and readable address-name snapshots on the order so later dataset updates do not alter historical orders.

When a complete permitted dataset cannot be obtained for an enabled market, state its coverage limitation, use the best maintainable country-appropriate hierarchy available, and provide a safe fallback for missing localities/postcodes (such as a validated manual entry or admin-maintained additions). Do not silently reject valid addresses just because the dataset lacks a locality.


## Aggregator integration by route

- **Domestic shipping within China for the China market:** when binding Kuaidi100, Kdniao, or another aggregator SDK/API, implement electronic labels. Request a shipment from an admin order through the server with order, sender/recipient, and required parcel details. Receive provider document ID, carrier, tracking number, and print data; return them to admin with preview, printing, and reprinting. Complete asynchronous responses through polling or verified callbacks. Acceptance of a request is not receipt of a tracking number.
- **China cross-border and markets outside China:** submit orders to the chosen aggregator and receive tracking numbers. Persist mappings between local orders and provider orders/parcels. Supply route-specific sender/recipient, parcel, and required customs data, prompting for missing business fields. Map synchronous results, polling, and callbacks to the correct order/parcel. Update carrier/tracking and enable tracking. If the product provides labels, save their reference and printing entry point. Order submission alone does not satisfy the domestic China label requirement.
- **All routes:** always allow manual carrier/tracking-number entry and editing, rather than making provider APIs the only fulfillment path. Both automatic and manual shipments support tracking. Without credentials, permit manual records while accurately showing unconfigured/unavailable tracking.

Check selected products, SDK versions, merchant contracts, and account permissions for order submission, electronic labels, tracking-number retrieval, print data, and tracking events separately. A tracking-only product is not full fulfillment. Disclose missing required capabilities and confirm a compatible product or supplementary service. Without credentials, implement adapters/controls and disclose untested integration without inventing numbers or labels. Rate quotes are not a mandatory added module. Label requests may incur fees: verify in isolated data/provider sandboxes, not by automatically purchasing live labels.

## Admin actions and states

Provide a Delivery methods admin screen for creating/editing delivery methods, descriptions, estimated delivery times, fees, display order, and enabled status. Order details show the customer's selected method and its description/estimate/fee snapshot alongside fulfillment actions: Request electronic label for domestic China aggregator shipping, Submit shipping order for China cross-border/markets outside China, Check synchronization, Enter/edit manually, Confirm dispatch, and Track shipment. Domestic China provides preview/print/reprint; other routes offer printing when the provider supports it. Without a valid label, do not report fake printing success. Do not assume a particular printer brand; browser/PDF printing is acceptable, with specialist printer integrations only when required.

Before submission/request, validate order eligibility, sender/recipient, parcel, and provider-required fields. Distinguish submitting, accepted, awaiting tracking number, printable label, failed/needs correction, and actually dispatched. Tracking-number assignment and label generation/printing do not mean handover to a carrier. Advance dispatch state and record dispatch time only after explicit confirmation or a verified actual-dispatch event.

Protect manual edits with admin permission, validate carrier/number, and record before/after values, actor, time, and reason. Customers cannot edit. Preserve original provider IDs and label versions; do not relabel an old document with a new tracking number. If edits affect provider state, use its official update or cancel/recreate process. If unsupported, show pending divergence rather than claiming both sides match. After changing the active tracking record, old callbacks must not overwrite it. Reprinting reuses the existing label without a new request or duplicate charge.

## Persistence and API consistency

Use suitable AddressRegion/PostalCode, DeliveryMethod, and Shipment/request/label models. Address data stores country, code, name, hierarchy level, parent, postal-code associations when applicable, source/version and update metadata. Persist delivery method configuration, including description, estimated delivery time, enabled status, fee rule, and ordering. On each order persist a snapshot of the selected country/region hierarchy, postal code and street detail, plus selected method/name, description, estimate, and charged fee in addition to shipment/order/parcel association, route, provider, provider order/parcel IDs, carrier code/name, tracking number, automatic/manual source, current version, request/sync status, label reference/format, dispatch time, tracking status/events/last successful sync, and safe error summaries. Secrets stay in secure server configuration, not requirements, browsers, or logs.

Use persistent idempotency keys/unique constraints and concurrency handling for submissions, shipment requests, provider events, and dispatch confirmation. Keep external requests separate from local transactions and reconcile with provider request IDs and query APIs. After timeout, query the original result before creating another order or requesting another label. Verify callback signatures and prevent replay using provider rules, validating provider order/parcel, current version, and legal transitions. Trust neither a browser-submitted tracking number nor just a local order ID in a callback. Synchronize cancellation/voiding when supported; preserve history.

Labels contain sender/recipient details. Preview/download/print endpoints require admin authorization. Provider signed links or print credentials must not enter the public media library. Customers access their own shipments/tracking through verified membership ownership or an order access key, without direct access to other orders' labels or personal details.

Call tracking providers server-side, normalize events/times, support refresh/subscription, caching, and rate limits. After a number change, bind the right provider/carrier. Retain old history without mixing it into the new shipment. Display last successful sync, no events yet, failure, and unconfigured states without fabricated nodes.

## Verification

Exercise country-appropriate cascading address selection and postal-code lookup for each enabled market; verify valid parent-child combinations, server-side tamper rejection, optional/unmapped postal-code behavior, street details, and persistence of readable address snapshots after data updates. Verify address dataset source/version/coverage and repeatable import when bundled. Exercise delivery-method admin create/edit/enable/disable, descriptions, estimates, and fee changes; verify checkout displays the configured description/time/fee for eligible enabled methods, requires a selection, calculates the selected fee server-side, includes it in the total, rejects tampered/disabled methods, and preserves the order snapshot after configuration changes. Exercise with local isolated data/provider sandboxes: domestic China shipment request -> tracking number/label return -> preview/print; China cross-border and markets outside China order submission -> tracking-number return/sync -> dispatch confirmation. For all routes, test manual entry, editing, persistence after refresh, and tracking, checking visible feedback, server responses, and data changes.

Also test missing fields, unauthorized access, provider failure, timeout/query recovery, duplicate requests/submissions, duplicate/out-of-order callbacks, old callbacks after manual changes, reprinting without recreation, and label creation not automatically marking dispatch. Without credentials or verified print output, mark blocked/unverified components separately. Buttons, screenshots, or compilation do not establish working fulfillment.
